# Decision Log — Syngraphē

Append-only log of the product's design decisions. New rows go at the top of the table. A decision is changed by a new row that supersedes it, never by editing the old one. Rows decided on a branch built beside another carry that branch's epic number — `DL-10-001` — and keep it after the merge; the rest follow one sequence.

The rows of release 0.1 are in [`decision-log-0.1.md`](decision-log-0.1.md); the ids continue from it.

| DL-0562 | 2026-11-12 | (Refines DL-0552 and DL-0553.) Where does a trace live, what does it record, how long is it kept, and how does a production call reach its prompt version's eval results? | **(1) A trace is a row in each organisation's own schema**, so tenant isolation stays the database's. **(2) Each trace records, for one call:** the documents and commits it read, or for a draft its base commit and text (DL-0553); the prompt version — one hash over the base prompt, the heuristic, the model and the effort; the model that answered; the provider's request identifier; the input, output, cache-read and cache-written tokens and the cost computed from them; the time taken; how the call ended — done, refused, failed, unparseable; the quotes withheld as fabricated and the detector's hits (DL-0559, DL-0561); the stored result, any *not right* mark (DL-0554); and the platform's release. **(3) Traces are kept for good**, the draft text in them included — a draft its author discarded too, since the traces are the platform's feedback loop for improving the agents; the erasure procedure (B-017) clears what a person's request reaches. **(4) The command that loads the prompts refuses a prompt version with no dated result at its target in `evals/`**, carrying the same hash, so every call in production traces to results that exist and pass. | A trace holds an organisation's references and drafts, so it belongs where the database already isolates that organisation. Each field answers a question someone explaining a result months later will ask — what was read, by which prompt and model, at what cost, and how it ended. Keeping traces whole keeps every past result explainable, and they are small: references, not copies (DL-0553). A prompt version that reached production without passing results would break DL-0554 (4) silently; refusing it at load makes the rule mechanical. Keeping a discarded draft's text exposes what an author wrote and withdrew; the owner accepts that for 0.2 and may revisit it (B-077). The alternatives that lost: the draft text cleared at discard; the draft text cleared when committed or after ninety days; everything deleted after a fixed period; a load command that warns and loads anyway. | `docs/technical-design.md` (the traces); `docs/data-model.md` (the trace table); `docs/runbook.md` (the load command); B-017's procedure | superseded — promoted to ADR-0024 |
| DL-0561 | 2026-11-12 | (Answers the residual of T-02.) How does a model call keep the document as data, and what remains when it does not? | **(1) Instructions live only in the system prompt** — the base and the heuristic; the document goes in the user turn inside a delimiter carrying a marker made fresh for each call, which the base prompt names as the boundary of data that is never an instruction; the answer returns only through the enforced output structure. **(2) An attempt to instruct the agent is made visible in two layers**: deterministic structural checks on every document a call reads — a forged delimiter, a chat role marker, the run marker's format — which hold in any language; and a field of every call's output in which the model quotes any text in the document addressed to an automated reader, which works in any language the model reads and costs no extra call. Each hit is a finding shown to the reviewer — *this document contains text addressed to an automated reader* — and **a notification in the application to the organisation's tenant administrators and to the platform administrators** — never by email, an exception to DL-0070 — naming the document and its version, never its text and never a person (DL-0113); no automatic step is taken against a person or a document. A marker the document cannot know cannot be forged by a fake closing tag. No phrase list is an industry standard, lists are evaded by paraphrase and translation, and a list keyed to a document's language misses a sentence in another; the available classifier models do not cover Ukrainian and carry licences the platform cannot redistribute. A notification names no person because a policy about the use of AI may quote such text innocently, and an administrator judges it. | DL-0560 | 2026-11-12 | (Resolves T-03 of the threat model; refines DL-0120.) | DL-0559 | 2026-11-12 | (Refines DL-0032 and DL-0120.) How are release 0.2's model calls cut, and how is each finding grounded, attributed and sorted? | **(1) One heuristic per call.** A finding's heuristic is the call's, never a label the model assigns, and changing one heuristic re-runs only its own evals. **(2) A finding's sources are the call's context, never the model's tag.** A cross-document heuristic runs on this document and one neighbour per call; the guidance heuristic on this document and the guidance; so each finding's sources — and with them its audience (DL-0021) — are exactly the documents the platform put in. **(3) Every finding quotes the passages it rests on, and the platform checks each quote word for word against the text.** A finding whose quote is not there is withheld from people and counted as an error in the evals; a finding offered with no quote is shown as a labelled suggestion. **(4) A finding is sorted by where its verified quotes sit**, against the line-level difference between the accepted version and the run: *introduced* when a quote touches a changed line and no standing finding of that heuristic matches; *pre-existing* when every quote is in unchanged text; *aggravated* when a quote touches a changed line and a standing finding of the same heuristic on the same passages exists; *resolved* when a standing finding's passage was changed or removed and the run does not reproduce it. **(5) The companion runs on the whole draft with the editor's changes marked**, and the platform keeps only the findings whose quotes touch a changed passage. **(6) The model reads the text without its entity markup**: no 0.2 heuristic relies on marked roles, actions or terms, since marking is done by hand and optional; the model reads roles, actions and timings from the prose. | The unit measured is then the unit run, and DL-0554's first criterion holds exactly. A quote that is not in the text is a fabrication, the sharpest signal of a wrong finding, and checking it costs nothing. Matching two lists of model findings is fragile — the same model on unchanged text words and splits findings differently — where the position of a verified quote against the version diff the platform already computes is deterministic and costs no call. The model sees the whole draft, so a new sentence that contradicts an old one is found. The alternatives that lost: one call per action, whose every composition is an unmeasured prompt; the whole review scope in one call, whose findings would reach only people who may read every document in it; the model's provenance tag, which `review-findings.md` had; an unverified quote shown as a suggestion; a second model call to pair and sort the findings; the companion told to report only what is introduced, with no filter; heuristics over the entity layer. | `docs/review-findings.md` § Rules (the agent no longer tags provenance) and § What is in the first cut; `docs/technical-design.md` (the prompts section); `docs/evaluation-strategy.md`; DL-0551 and DL-0555 (their first-cut clauses, corrected in place); `docs/prd.md`; `docs/user-stories.md` ST-0083 | superseded — promoted to ADR-0022 |

| DL-0554 | 2026-11-12 | How is release 0.2 known to have worked, and what does a person do with an analysis that is not right? | **Four criteria, all of which must hold:** (1) every heuristic that ships is at its eval target, with its results dated and committed; (2) an editor and a reviewer complete a full cycle with the analyses on the send-for-review screen and in review, without meeting prompt, model or heuristic vocabulary; (3) in production, the share of analyses that people mark as not right stays under a ceiling the evaluation strategy sets for each action, read from the traces; (4) every model call in production traces to its prompt version and that version's eval results. **One control on each analysis — *not right* — joins release 0.2.** It **informs whoever develops the platform that the software's output is wrong**: it is a signal about the analysis, never a judgment of the document's sense or a disagreement with its prose.
