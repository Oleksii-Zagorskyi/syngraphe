# Technical Design — Syngraphē

> [!note] Walking skeleton
> Structurally complete, deliberately thin. Sections resting on unanswered questions name the question inline.

## Stack

| Layer | Choice | Status |
|---|---|---|
| Application | Django, Python | Decided (seed) |
| Git access | pygit2 inside Django, on bare repositories it owns; the `git` binary in the image, for blame | Decided (DL-0030, DL-0042, ADR-0002, ADR-0011) |
| Database | PostgreSQL, schema per tenant | Decided (DL-0029) |

| Runtime | Containers: web, PostgreSQL, Redis, Celery worker | Decided (DL-0086, DL-0134) |

| Markdown parser | markdown-it-py on the server and markdown-it in the editor, bound to the whitelist and configured from one specification file | Decided (ADR-0010) |

## Architecture

**Django owns the workflow. Git is a library, not a service.** Rationale, consequences and rejected alternatives: [`ADR-0002`](adr/ADR-0002-django-owns-the-workflow.md).

```
Browser (the interface in the person's language, Ukrainian or English)
   └── Django — the only authorisation surface
        ├── workflow: holds, versions, acceptance, disputes, editions, rejections,
        │             comments, entities, findings, heuristics, roles, tenants
        ├── pygit2 on bare repositories: init, commit, read, diff, revert, tag; the git binary for blame (ADR-0011)
        └── agent jobs: sandboxed containers the platform starts
```

Forgejo is gone (DL-0042). Edits accumulate in the application and are committed on a user's behalf, so a forge could never authenticate per commit; once identity leaves and the events that start agent runs are the platform's own, a forge has nothing left to offer. Git usage is init, commit, read, diff, blame, revert and tag — no branches, no merge (ADR-0003).

## Runtime

**Development** runs on a development host; **production** runs behind the operator's reverse proxy, which terminates the public TLS (DL-0281). Both are the same containers — web, PostgreSQL, Redis and a Celery worker — and the difference is where they run and what backs them up.

- **worker** from stage 1, not stage 2, with **render** beside it: rendering an export is slow and does not belong in a request, and `EXPORT_JOB` is asynchronous — `render` consumes its own queue on a network with no way out (ADR-0013). It also computes per-line authorship after each commit into `LINE_AUTHORSHIP` rows, which the author view reads rather than blame (DL-0135, ADR-0011). **Three rules keep the cache off the interactive paths (ASR-21):** the pending run's own lines are attributed at render by a blame of the head bounded by the accepted version and never wait for the worker; older text whose version has no rows yet renders without an author, never blocking, and the reconciler asks the worker again for a kept version without rows; a bounded blame whose base version has no rows falls back to a cold blame. **Rows are kept for the head and the latest accepted version only**; an older version's authorship is computed on demand — asked by its historical page with *Show edit authors* on, one job at a time per version — kept a day, and swept hourly by beat (DL-0266, DL-0489). **The access history is a query, not a replay** (ASR-18): for a document at a moment, the latest change of each link, right and membership at or before it, one query per kind of row (`DISTINCT ON`), whatever the history's length.
- **Redis** is the broker and result backend, and is **not in the backup set**. It runs without persistence on purpose: every queued task has a row behind it, so a lost entry is re-enqueued from its row by the reconciler. A broker that has to be restored is a second store holding state, which is the thing the write protocol exists to avoid.
- **git working area** — a volume holding the bare repositories Django owns, one per document.
- **Stage 2 agent runs** are ephemeral container jobs started by a dedicated runner service consuming the queue. The job assembles the context, makes one request through the **provider interface**, and parses a structured result — it does not decide what to read, because the review scope already did (DL-0120) — never by the web process, because a process that can start containers turns a web vulnerability into a host compromise. Each run mounts read-only exactly the repositories in its review scope and nothing else, and its egress is limited to the model endpoint.

**As built, the stack is six Compose services** at the repository root: `web` — gunicorn, which migrates every schema, seeds the language lists and collects the static files as it starts, then serves the application and its own static files (DL-0285); `worker` — Celery, with the periodic tasks' scheduler inside it, the outbox's sending every minute among them (`mail.send_outbox`, DL-0203); `render` — Celery on the `render` queue alone, making exports on a network marked internal that it shares with `db` and `redis` and nothing else (ADR-0013); `db` — PostgreSQL 16, its log archived by pgBackRest; `backup` — the nightly base backup and the state the worker reads (ADR-0019); `redis`. Each receives only the configuration its job needs: the mail key, for one, reaches `web`, which encrypts a sending password, and `worker`, which decrypts it to send, and no other service (DL-0384). `/health/` also reports the backup's state — the newest clean marker's age, whether any repository is failing (never which), the last segment archived and the log waiting — without letting it change the status code (DL-0295). Only `web` publishes a port, on the loopback, for the host's reverse proxy; the proxy's forwarded client, scheme and host are honoured only from `TRUSTED_PROXIES` (DL-0283, DL-0292). A production shape overrides the base file rather than editing it: `deploy/compose.prod.yaml` adds a seventh service, `front`, an nginx that terminates the installation's TLS on the one published port, buffers requests and forwards to `web`, which then publishes nothing; the data moves to bind mounts under one directory (DL-0281). The front is configured by two files in `deploy/front/` rather than one `nginx.conf`: a template the image renders at start, and a helper that turns the header the operator's proxy carries the client's address in — a per-installation value — into the nginx variable the template forwards as `X-Forwarded-For`. The application sets `Content-Security-Policy` on every response from `syngraphe.content_policy`, second in the middleware list so that the static files WhiteNoise answers carry it too; the front passes it through, re-adding only its own three headers (DL-0493). Gunicorn runs threaded workers, two workers of four threads each, so an idle connection holds a thread, not a worker (DL-0347). An attachment is downloaded at `/document/M/attachment/n/`, from the version the reader may see, through the document page's own gates (DL-0342).

Sizing is not driven by the agents — their work is mostly waiting on a model API. Memory for repository working copies and PDF rendering is the constraint.

**Off-host backup is a production requirement** (DL-0118): a copy of the database archive and of every repository has to leave the host, or the scope agreement's *nothing is ever lost* is true only until that host fails.

## The write protocol between git and PostgreSQL

Two stores, one record. Without these rules the crash states are undefined and the tamper detection T-07 relies on has nothing to compare (DL-0111).

**Git is the commit point.** The ref update is the moment a version, an acceptance, a return or an approval exists. Rows are **derived idempotently** — by the request that made the commit, and again by a **reconciler** that replays any commit lacking its row. A row is never the authority for something git holds.

**One repository per document**, at `tenant-N/document-M/` — the tenant's platform number and the document's number in its tenant (ADR-0008). Never by title: a directory named by title puts document titles, including a confidential guidance document's title, into filesystem listings, backup manifests and operator shells that the access table does not govern.

**A single-writer lock per document** covers every ref update: the file `tenant-N/document-M.lock` beside the repository, taken with `flock` by `web` and `worker` alike and by an operator's shell, always before any database row lock. It is almost uncontended, because the editor's hold already serialises human editors, but it still has to exist: acceptance and any stage 2 worker write are not covered by that hold; undoing a contribution is made inside the reviewer's own hold (ADR-0015).

**The passport wins over the row.** Where they disagree, the reconciler reports it and never changes the passport; the interface believes the passport.

**Document creation is the one two-store write.** The row is written in a `creating` state; the repository is initialised and receives its first commit, of kind `created` (DL-0268) — `document.md` built from the organisation's template (DL-0169); the row becomes `active`, reaching only its author until groups are linked (DL-0260). The reconciler **finishes** a creation that stopped — except a copy, which it reports and never finishes (DL-0455) — and **recreates** the row of a repository without one, with no access — never deleting a repository.

**Backup never restores the database past the repositories** — the tooling and the restore are [`ADR-0018`](adr/ADR-0018-backup-and-restore.md) and [`ADR-0019`](adr/ADR-0019-backup-when-something-fails.md). The superset property holds per document: history is append-only and there is no cross-document commit, so each repository copied after the database's recovery point contains at least what the database knew about it. The repositories are bundled every ten minutes, and every run leaves a marker listing any repository that failed; a restore of the whole host takes the database to the time the newest run with no failure began, or to the last good moment if that is earlier, and to the end of its archive only when recovery cannot reach that time (DL-0294, DL-0296, DL-0314); markers are kept as long as the oldest chain any repository keeps (DL-0316); and a failure of the database alone, the repositories intact on the host, restores it to its latest archived point (DL-0276). Two hazards, neither about the number of repositories, and one rule:

- A repository copied **while it is being written** can yield a ref pointing at an object the copy missed. Each bundle is written **under the repository's writer lock** and verified and copied after the lock is released, so no commit waits on the store (DL-0301).
- A restore leaves git ahead of the database and the reconciler repairs that, but **database-only state after the recovery point is gone** — holds, access changes, and above all **drafts**, which ADR-0003 makes load-bearing because a session has no intermediate commits. The database therefore needs **continuous archiving with point-in-time recovery**, which ADR-0018 gives it.
- A repository restored **without its row** is recreated from `document.md`'s frontmatter — title, language, and the appendix and attachment lists — with **no access rows at all**, and the tenant administrator is notified. Fail closed, the same instinct as an untagged finding.

**Housekeeping for many small repositories.** Initialise from an empty template, or every repository carries a dozen sample hooks. Schedule a **nightly repack per repository under its lock**, before the base backup (DL-0313), because a library that writes commits does not repack and each version leaves loose objects; pruning removes only unreachable objects, and in an append-only linear history the only unreachable objects are debris from failed writes — so this does not touch ASR-02, and that sentence belongs beside the job or nobody will dare run it.

**What is given up, recorded rather than discovered.** There is no commit meaning *the corpus as of this moment*; nothing needs one, because an analysis is keyed by each document's own content state (DL-0078). And a cross-document generated view has no repository to live in — when B-003 is taken up it needs a per-tenant derived store, not a home inside any one document.

## Tenancy

A tenant is a fully independent group of users or a separate business (DL-0003). The tenancy mechanism as a whole — the schema per tenant, the one middleware that resolves it, the guard and the per-schema migrations — is [`ADR-0017`](adr/ADR-0017-schema-per-tenant-resolved-per-request.md). **A tenant is recognised from the host** when it has its own domain (`TENANT_DOMAIN`), and from the session on the application's main domain; a person signing in on a tenant's domain lands in that tenant, and switching tenant moves between domains and may need signing in again (ADR-0008). Tenants share nothing but the heuristic catalogue their copies are seeded from.

- **Database — schema per tenant** in PostgreSQL (DL-0029). Isolation is enforced by the database, not by application code: crossing it requires getting a whole request's `search_path` wrong rather than one query's `WHERE` clause. Migrations run per schema; platform-level tables live in a shared schema.
- **Repositories** — a directory per tenant holding one repository per document, pairing with schema-per-tenant. DL-0003's mapping of a tenant to a Forgejo organization lapses with DL-0042.

## Identity and authorisation

Both are Django's (DL-0042, superseding DL-0015). Groups holding rights, linked to documents, are the only permission model in the system (ADR-0007) — one authorisation surface, per ASR-07. The MCP contract, that an external agent holds exactly its user's rights, is a property of the same authorisation path the browser uses.

Principle of least privilege throughout: the burden is on expanding access, never on restricting it.

**Developers are not an application role** (DL-0210). Django's own administration interface is reachable only by operator accounts with its superuser flag, created from the command line; it is never linked from the application, is served only on the platform's main domain, sits at a non-default path, and every use is audited. Platform and tenant administration are the application's own pages.

**People enter by invitation** (DL-0107, DL-0374). An organisation's administrator invites an address with the groups it joins: in one transaction the person is created with no usable password when the address is new, the membership is created, the groups are joined — their entries written without email, the invitation's own email being the one (DL-0399) — and an `INVITATION` with a hashed, seven-day token is written with one email queued. The link opens `/invitation/<token>/`, a page outside the shell served to anyone; it sets the password under DL-0284 and signs the person in. A reset is the same shape: `/reset/` answers one page for any address and, only for an account with a usable password, writes a `PASSWORD_RESET` row with a one-hour token and queues its email; each request is counted on a throttle row of its own per client (DL-0408). Spending any link ends every other open link to the person; a changed password signs every other session out by the framework's own check of the password's hash. A link's token is a credential while valid, so it is kept out of the stored email once sent (DL-0406) and out of every log line (the application's, the application server's and the front's). Two of these acts work in schemas the request did not resolve, and only they among the people acts enter one inside a request, through the schema context manager: a reset's request enters the schema DL-0383 chooses for its row and email, and each block enters every organisation whose holds it ends (DL-0401).

**Blocking ends what it closes** (ADR-0007, DL-0256). A membership's block, a person's own block and an organisation's block each run `identity.blocking.end_holds` inside their own transaction: every open hold the block closes is released as `blocked`, under the document's writer lock and then its row, a draft with edits kept (DL-0514), a lock busy past its wait refusing the whole block. A take locks the taker's membership before the document's lock, so a hold is never taken while a block is written. Platform administrators are told when a person blocked in some organisations stays active in another, and when an organisation is left without an active administrator; an organisation's administrators are told neither (ASR-17). A person's own block is shown on no organisation's page (DL-0398).

**The interface's language is the person's** (DL-0498, DL-0501). Each person chooses Ukrainian or English on their own account page, `/account/`, reached from the user menu as *My account* — the page shows their address read-only, the language with *Apply*, and, apart at its foot, *Block my account…* (DL-0499, DL-0500). The choice is a `language` row of the person's preferences in the shared schema, applied to each request by a middleware after authentication; a person without one, and every page before sign-in, gets the installation's default — except a reset or invitation page opened from its link, which uses the preference of the person the link belongs to. The language of a document — its text, its numbering, its exports — is the document's own and never follows the person's. The middleware is `identity.middleware.LanguageMiddleware`, placed right after the tenancy middleware; `LANGUAGES` holds the two codes the catalogue serves, and `DEFAULT_LANGUAGE`, the installation's default, must be one of them or the application refuses to start.

**Switching organisation.** A person with several active memberships switches from the shell: on the platform host the session's organisation changes; on an organisation's domain the answer is a page carrying the link to the other's default domain, or to the platform host, where the choice is confirmed by the person's own POST (DL-0497).

## Who performs git operations

Django, through pygit2, on bare repositories it owns, with the `git` binary in the image for blame — pygit2 has no bounded blame, no excluded commits and no reverse walk (ADR-0011) — **Forgejo was dropped at DL-0042** (ADR-0002). The reasoning was the owner's: edits accumulate in the application and are committed on a user's behalf, so a forge cannot authenticate per commit and cannot hold the authorisation; and once the events that start agent runs are the platform's own, forge runners add nothing either.

The operation set is small because the model is linear (ADR-0003): **init, commit, read, diff, blame, revert, tag** — `init` because creating a document creates a repository (DL-0111). No branches, no merges, no conflict resolution.

**Commits carry no personal data** (DL-0088, DL-0093). The git author name is the Django user identifier; the author email is a per-user non-routable address, `{user-id}@users.noreply.syngraphe.local`, so authors stay distinct to any tool that keys on email. The domain is fixed here, once, because it is baked into every commit ever written and changing it later splits one author into two. The mapping to a person lives in PostgreSQL, and a deletion request is answered by removing that mapping rather than by rewriting history — which is what keeps ASR-02 and a person's right to erasure from colliding.

**A contributor map travels with an export, never with the history.** Identifier to display name, generated at export and backup time from the database and never committed. It answers the cost of pseudonymisation — a repository whose history reads as opaque identifiers is not portable evidence — without putting a name anywhere immutable. Erasure changes what the next export contains and nothing that already exists.

What was given up is the forge's web interface for inspecting a repository when something breaks. The replacement is the `git` command line on the host, plus read-only repository views for the platform administrator.

## Repositories and access

**One repository per document** (DL-0111), at `tenant-N/document-M/` (ADR-0008). Confidential guidance is an ordinary document with restricted access (DL-0051, superseding DL-0008). The granularity is what makes the agent's mount list *be* the review scope, so the editor-facing run has no guidance on its filesystem at all.

Access is **data with history** (ASR-08): groups, their rights, their members and their links to documents, every change carrying a timestamp and an actor, editable only by a tenant or platform administrator (ADR-0007). A confidential document is one linked to few groups; a new document is linked to none and reaches only its author.

The condition the old design relied on is now explicit rather than structural: **no user ever receives raw repository access, and every export is per document**. Both are enforced by the application because the application is the only path to the repository.

## Document storage and diff semantics

A document is **its body, zero or more appendices and zero or more attachments**, all in its own repository (DL-0165, DL-0166):

```
tenant-N/document-M/          # repository root, one per document (DL-0111, ADR-0008)
├── document.md       # frontmatter: title, language, appendix and attachment lists · body: the main text
├── appendices/       # one Markdown file per appendix, named by its number: 1.md, 2.md
├── attachments/      # one opaque file per attachment, named by its number
├── entities.yaml     # role, action and term definitions
├── images/           # uploaded binary assets the text embeds
├── analysis/         # editor-facing companion analyses (stage 2)
└── passport.md       # review and approval decisions (DL-0041)
```

### Appendices, attachments and the title page

- **`document.md`'s frontmatter lists the parts**: appendices in display order, each with its identifier and title; attachments in display order, each with its identifier, title, original file name and SHA-256 hash. Adding, removing, renaming, replacing or reordering a part is a change to the document, versioned and reviewed like any other (DL-0168), and a repository restored without its row recovers every part from this one file.
- **An appendix** is a Markdown file under the same whitelist as the body, holding **exactly one `#` section**, whose heading is what the finished document shows. Its title in the frontmatter names the appendix in the interface and its exported file, and is never rendered in DOCX or PDF. An appendix has no appendices or attachments of its own.
- **An attachment** is stored as uploaded and never parsed, rendered or read by an agent. Its size is capped per tenant, 5 MB by default. Replacing it writes a new blob at the same path, so earlier versions stay in history; a download serves the original file name.
- **A part changes in the holder's draft and nowhere else** until the draft is committed (DL-0442). The draft holds each appendix's text under its own key and the new or replacing files beside it; the commit decides the part rights again on what the draft changes in net — a right lost since staging refuses the commit, naming the part — writes exactly the appendices the draft lists, each held to the whitelist and to its one `#` section and normalised, and checks every listed attachment's bytes against its entry. Creating and deleting need the part rights of a linked group; renaming and reordering need *edit*; the author of a document no group is linked to may upload and replace attachments (DL-0445). A reviewer's *revert* of a part operation needs *accept* alone and is committed as part of the correction (DL-0446).
- **The title page is not stored.** When a document has one — its switch in the frontmatter, set at creation from the organisation's template and changed by the holder as a draft change committed with the run (DL-0463) — it is rendered at export from the document's details through the organisation's **title page layout**: which of title, number, type, edition, approver, approval date and the document's own title-page text it shows, in which order, left or centred, stored as data on `DOCUMENT_TEMPLATE` and empty for the default form (DL-0462). The **approval line** is always there at a position of its own: the approver, the date and the edition on the canonical view, *not approved* to the edition it departs from on any other (DL-0360, DL-0475). The title-page text is the one authored detail — plain text in the frontmatter, at most 500 characters and 8 lines, line breaks kept, no control, reordering or invisible format character but the two joiners some scripts need (DL-0476, DL-0483). No logo (DL-0467).

### The constrained Markdown subset

**This list is the whitelist.** It is normative and it is the only place the set is decided — `src/editing/whitelist/spec.json` is its machine-readable form, changed with it, and every test or harness reads the set through that file and never restates it, and a construct absent from it is absent from the product (DL-0046, DL-0100).

| Construct | Form | Note |
|---|---|---|
| Headings | `#` to `####` | Depth capped at four; numbering is a render rule |
| Paragraphs | blank-line separated | One sentence per line on disk, never visible |
| Lists | ordered and unordered, nesting to three levels | No task lists |
| Emphasis | `*italic*`, `**bold**` | |
| Underline | `[text]{.underline}` | An attributed span, not `<u>` |
| Entity spans | `[CMO]{.role #cmo}` and the other types | Defined in `entities.yaml` |
| Mentions | `[text]{.document #12}` | Another document named by its number: one to ten ASCII digits, the first 1 to 9; one without a number reads as its words; never inside an entity span, nor one inside it (DL-0436) |
| Quotes | blockquote, `> text` | Paragraphs and lists inside; no nested quote, callout or table (DL-0238) |
| Callouts | typed blockquote, `> [!note]` | Types: note, warning, example; paragraphs and lists inside, no nested quote, callout or table; the marker stands alone on its line, and text written after it moves to the first paragraph (DL-0238) |
| Tables | pipe tables | At the top level only (DL-0239); no merged cells, no nested blocks; the row is the unit |
| Images | `![alt](images/name.png)` | Repository-local paths only; every image stands as a paragraph of its own, however it arrives — one inside a sentence is refused (DL-0232, DL-0253); a reference to an image the document does not hold is refused when the text is committed (DL-0439) |
| Links | `[text](url)` and repository-local paths | |

Everything else is outside the subset: raw HTML, scripts, footnotes, definition lists, headings below depth four, task lists, nested tables, merged cells, horizontal rules, code blocks, math, and any remote image or stylesheet reference. The editor offers exactly the set above and nothing else; anything outside it is **rejected at edit time with a message**, never silently dropped. Pasted Markdown that falls outside the set is refused with the offending lines named, and the user is offered a conversion — removing or rewriting what the set does not allow — previewed before it is applied (DL-0171). The message links to a help page listing the set, generated from the same specification as the editor schema and the parser configuration.
- **One specification, two parsers** (ADR-0010). The editor's markdown-it and the server's markdown-it-py are configured from one specification file; the span, callout and validation rules are written once per language, and a conformance suite in CI holds them in step — for those rules the weaker of the two controls V-04 weighed.
- **The whitelist binds the parser, not only the editor** (DL-0096): raw HTML disabled, no script, no remote image or stylesheet references, and no network for the PDF renderer. *Raw HTML disabled* means never rendered: the parser recognises raw HTML only to refuse it with a message, because left unrecognised it would pass through as literal text without a word (ADR-0010). Text arrives by paste and by import as well as by typing, so a rule that only the interface enforces protects nobody.
- **Tables** are pipe tables: one row per line, inline content only, no merged cells, no nested blocks (DL-0100). Inside a table the **row** is the unit of diff, authorship and per-author undo — a cell cannot hold a line break, so the sentence stops being addressable there. The normalizer gives every row exactly one spelling: one space inside each cell edge, no alignment padding, a delimiter row keeping only its alignment colons. Without that, padding from an editor, a paste or a prettifier rewrites every row when one cell changes, and each rewritten row is re-attributed to whoever touched one of them.
- **Entities** are attributed spans — `[CMO]{.role #cmo}` (a synthetic example), `[obliged to approve]{.action}`, `[10 days]{.term #timeout}`. Real Pandoc syntax, so it survives every render target and stays machine-readable. Definitions live in `entities.yaml`; the spans mark occurrences. The editor never shows the syntax: a user selects text and marks it. Wherever text is rendered — reading view, editor, DOCX, PDF — marked text carries a distinct formatting set by the stylesheet (DL-0184).
- **One spelling per construct** (DL-0240). Text inside the subset but spelled otherwise is accepted and rewritten by the normalizer: `-` bullets, `N.` ordered markers numbered in sequence (DL-0324), a nested list indented by its parent's marker width, `*italic*` and `**bold**`, an entity span outermost when marks nest, `#` headings without closing hashes, pipe tables with edge pipes, a callout marker alone on its line, and a bullet list each item of which holds one numbered item — `- 1. Text` — as the numbered list it means, while a list mixing numbered and plain items is refused (DL-0441). A heading's own number, typed before its text where it equals the number the outline gives it, is taken away on load and from the lines a paste into the source view brings. A paragraph typed over several lines in the source view is joined into one line on the switch, and once typing pauses the notice line names the first such paragraph's lines, and how many more; the loader reports each line it joins, never refusing for it (DL-0441). A literal `<` is stored escaped, and so is an `&` that would begin an HTML entity, so text never reads as markup.
- **Normal form:** one sentence per line; a server-side normalizer runs before every commit (DL-0046, ADR-0012). Paragraph boundaries are blank lines — Markdown's native rule, not a convention imposed on it — and the renderer joins the sentences between them into one paragraph. The user never sees or manages a line break — not in the reading view, the rich editor, the source view or any export. The source view and a Markdown export write each paragraph as one line, entity marks included exactly as stored (DL-0184); the normalizer restores the stored breaks on the way back in (DL-0181).
- **A stored line is never re-normalised** (DL-0112, ASR-20). No normalizer rule — the splitter, quote and dash typography, Unicode composition, the removal of invisible characters, the canonical table row — is ever applied to a line its edit did not touch. *Touched* means the submitted line differs from the stored line **after canonicalising the submitted one**, so a prettifier that pads every table row produces rows that canonicalise back to the stored bytes and count as untouched.
- **What is read is what is stored** (DL-0486, DL-0487). The marks that reorder text — the bidirectional embeddings and overrides, U+202A to U+202E, and isolates, U+2066 to U+2069 — are refused by both rule sets, each named by its line, as control characters and the line and paragraph separators are. Every other invisible format character (Unicode category Cf) — a zero-width space, a soft hyphen, a word joiner, a direction mark, the byte-order mark — is accepted and removed: by the normalizer from the text the edit changed, and from what is pasted into the formatted view. The zero-width non-joiner and joiner, U+200C and U+200D, which some scripts need, are kept. A construct holding nothing but such characters — a list item, a span, a bold run of a zero-width space — reads as empty and is refused as what it reads as, by its line; so is a reordering mark spelled as an entity, `&#x202E;`, which the parse decodes. A stored line keeps such a character until it is edited; a stored reordering mark makes the text refused when the editor opens it, the line named in the source view.
- **Quote and dash typography** (DL-0273). Straight double quotes around a run of text become the document language's quotation marks — `«…»` for Ukrainian, `“…”` for English; a spaced hyphen between words becomes a spaced em dash; a doubled hyphen becomes an em dash; three dots become an ellipsis. It rewrites text content only, after the splitter's masking — never a link destination, an attribute block, image syntax or a table's delimiter row. It is the *typography* stage below, run on what *reuse* left to rewrite and before any boundary is placed, over every touched line, a heading and a table row's cells included, though the splitter divides neither; the parse-preservation check therefore compares the typeset text before and after the split.
- **What reaches the normalizer.** The rich editor submits each paragraph with a line break at every stored sentence boundary it kept (V-03); the source view and an outside paste submit each paragraph as one line. **The normalizer relies on neither**: it joins each submitted paragraph's lines and treats every path alike. The editor's breaks only make an untouched paragraph arrive byte-identical to its stored lines.
- **The normalizer is a function of two inputs**, the previous version and the submitted text. Within each paragraph it aligns the new text against the old, carries the old boundaries across unchanged spans, and runs the rules only over changed spans widened to the whole old lines they overlap — the alignment of the *reuse* stage below.
- **The normal form is therefore path-dependent.** The same text can legitimately be stored with different line breaks depending on its history. **The stored newline is the authority** — a check that re-runs the splitter over a file and compares is not valid, and the line structure cannot be rebuilt from the text, unlike the search and navigation indexes.
- **Normalisation preserves the parse** — an invariant checked on every write. A wrong boundary degrades granularity, not correctness: an over-split renders identically and anchors identically. The one way a boundary can be *wrong* is a break inside an inline construct, and this invariant is what catches it.
- **The splitter is the platform's own** (ADR-0012), rules parameterised by data. Before any rule runs, link destinations, attribute blocks and image syntax are masked, so no boundary can fall inside them. A boundary candidate is terminal punctuation (`.`, `!`, `?`, `…`) plus any closing quotation marks or brackets that follow, then whitespace. `!` and `?` always end a sentence; `…` only before a capitalised word. A full stop does not end a sentence before a lowercase letter or a digit, after a single capital letter (an initial), or after an abbreviation in the language's *never final* list; after an abbreviation in the *may be final* list it ends the sentence only before a capitalised word; otherwise it does. Each sentence inside a multi-sentence quotation is its own line, and the boundary after a quotation falls after its closing mark. The two lists are per-language data in the `LANGUAGE` table, seeded from the spike's fixtures and edited by the platform administrator; the rules do not change per language. Every boundary the splitter places is checked by the parse-preservation invariant above; a boundary that fails it is not written — the two sentences share a line — and the write proceeds. The normalizer version recorded per commit (below) names the rule set and the revision of the two lists it loaded, so a list edit is a new normalizer version and a line's split can always be traced to the lists that made it.
- **The normalizer version is recorded per commit**, not per document — one document holds lines split by several versions at once, so a per-document field would be untrue on the day of the first upgrade.
- **Moved text keeps its stored lines** (DL-0244). A paragraph cut and pasted elsewhere arrives as a deletion and an insertion. Before anything is split, in order: whole paragraphs equal to a stored paragraph anywhere in the file reuse its lines; other paragraphs are aligned in place (above); in what is still unmatched, the previous version's stored lines are found where they stand as sentences of their own — each end an edge of the paragraph or a sentence's end — longest first, and reuse their bytes, never out of the middle of a longer sentence (DL-0323); only the remainder is split. A stored line whose bytes change — a list item renumbered — is touched (DL-0324). Which author a tie between identical lines keeps is the authorship worker's (ADR-0011). **The stages, in order** (DL-0317): *canonicalise* each submitted paragraph and decide *touched*; *reuse* — whole paragraphs, alignment in place, stored lines standing as sentences; *typography*; *split*; *check* every new boundary by the parse-preservation invariant.
### Rendering, styles and layout

- **Heading numbering is a render rule** derived from depth: `#` is 1, `##` is 1.1, `###` is 1.1.1; a skipped level counts as 1, so a `###` directly under a `#` is 1.1.1 (DL-0327); a paragraph before the first heading carries its index alone, and a table or an image is not a clause (DL-0330). **Each appendix numbers its own headings from 1**, and a reference into one from elsewhere names the appendix by its title in front — *Approval matrix, 1.1-3* (a synthetic example) (DL-0444). Never stored, so moving a section renumbers everything and breaks nothing. Comments and findings anchor by quoted text (DL-0027). A prose reference such as *"as defined in clause 4.2"* is ordinary text; keeping it true as a document is restructured is a stage 2 heuristic, backlog B-015.
- **Style is the organisation's stylesheet**, one per organisation, authored by its tenant administrator; every document uses it, or the platform's default look while it is empty — no document chooses another in release 0.1, and the Info page says which applies (DL-0465; several per organisation is a backlog row). **It is an allowlist** (DL-0464): properties of type, colour, background, borders, spacing, alignment, page size and margins; `@page` and print rules; selectors of the platform's own elements and classes; a `font-family` installed in the image or a generic; nothing that fetches — `@import`, `@font-face`, `url()`, any function but a colour's — and no `content`, `display`, `visibility`, `position` or `opacity`; each refusal named by its line. The one checker runs at *Apply*, at the sample, at serving and at every export, so a row written before a rule tightened reaches no reader. **It applies to every read-only rendering of document text** — the reading view, comparisons, historical pages, notices — served from the platform's own route at an address that changes with the text, each selector confined to the document's text; the editor keeps the default look. **The platform's own sheet comes after it**, every declaration `!important`, which the stylesheet may not write: the approval line on its own white box at fixed values, the marks of a change in their own colours and their words in the platform's ink (DL-0477).
- **One parse for every target** (ADR-0013). The reading view is the HTML the server's parser renders — entity spans and callouts as classed elements the stylesheet addresses, sentences joined, clause and heading numbers attached as labels at render. PDF is weasyprint over that HTML with fetch failures fatal and a fetcher limited to repository files; DOCX is Pandoc over that HTML with the platform's classes mapped to named Word styles, their look given by a reference document derived from the stylesheet (DL-0465). The validator gates every export; a renderer's warning is never a pass. The renderer rules for spans, callouts, soft breaks and labels are a fourth piece of code beside the three ADR-0010 names, and exist server-side only — the editor renders through its own document model — so the conformance suite fixes their output rather than a twin.
- Hunks are classified **sense** or **style**. Style hunks **collapse** in the review surface and are accepted **with the run** — they do not auto-accept, because acceptance is a document-level act with no per-hunk step to skip, and a classifier deciding a change needs no human eyes would contradict ASR-04. A changed sentence is style when, formatting marks and the normalizer's typography set aside, its words and what it points at — link targets, images, entity spans — are unchanged; a sense change shows the new wording with its formatting, the inserted words marked inside it and the removed ones struck where they stood (DL-0331); two sentences at one place with less than half in common are shown as one removed and one inserted.
- **A section is a heading.** Structure is the heading hierarchy of `document.md` and of each appendix, and restructuring a document is editing its text. A section is a range of a file, never a file of its own.
- **Images** are ordinary git blobs — **no LFS** (DL-0066). PNG, JPEG and GIF are accepted and a per-image size cap is enforced on upload; HEIC and every other type are refused with a message, never converted; metadata is stripped, but for a JPEG's orientation tag, kept so a photograph shows upright (DL-0074, DL-0242, DL-0472). **An image pasted or dropped into the editor is an upload like any other** and always stands as a paragraph of its own; one known only by a web address is never fetched — it is left out of the paste with a one-line notice (DL-0232). A change to an image cannot be read as a diff, so the review surface flags it and renders before-and-after (ASR-04). **An image is named by its content**, `images/<sha256>.<ext>`, and checked and stripped without being decoded, held to 40 megapixels and 10,000 pixels a side (DL-0439, DL-0472). **It is served to its reader from the repository** at the newest version their ceiling reaches that holds it, laid out no wider than the text; a draft's images to the draft's holder through the draft's own route, from the draft or the commit it was taken from (DL-11-006); a correction notice's to its recipient through the notice's route, only the images of its own passages, read where each passage was read. Agents never read images (DL-0168). Revisit LFS only if a repository's size becomes a measured problem.
- **Clause numbering** is derived at render, never stored (DL-0065): `1.1-3` is section 1, subsection 1, clause 3 — each paragraph of text is one clause; the hyphen separates the heading path from the clause index, and heading depth is capped at four. A heading's number stands in the heading; a clause's in a non-editable gutter outside the editable region — in the editor as in the reading view and the PDF, recomputed as the text changes (DL-0363). The derivation has two twins, `rendering/numbering.py` on the server and the editor's `gutter.js`, held to one shared case file so a reader and an editor never see different numbers. A finding or a comment anchors by **quoted text** (DL-0027) and displays the current number — the number is a label, never an address.
- **Storage layout is flat.** One repository per document under the tenant's directory; the nested tree a user sees is Django metadata, and a move never touches a path (DL-0058, DL-0111, ASR-15).

## Versions, holds and history

- **Taking the document** opens a draft. It persists server-side, is invisible to others, and is not a version. There is no Save control.
- **The editor is a view over the draft** (ADR-0006, DL-0517). *Edit* opens the whole document's editor on the draft at once: a document is shown either to be read or to be edited, and there is no section editor. A draft the whitelist refuses opens in the source view with each refused line named. The same draft open in two browser tabs is two editors over it, and capture settles which stops. Every editor writes into the one draft of the one hold, and the draft its capture leaves is within the size allowed.
- **Captures are checked against the draft.** An editor remembers the draft's text as it opened it, and the server accepts its capture only while the draft is unchanged since the editor last saw it. An editor whose draft changed underneath it stops, turns read-only, and shows its unsaved text as changes against the current draft for the user to carry over by hand.
- **Open editors are known to the server** by heartbeat. Finishing, discarding and an analysis request are refused while any editor is open — on the page, *Finish editing*, *Release the document* and *Discard my edits…* capture what is typed and close the editor before they act (DL-0518); an editor whose tab closed without closing it times out. An editor captures 750 ms after the last keystroke, and at once when it loses focus or its page is hidden; it beats every 30 seconds, and one silent for three minutes is closed by the worker, which looks every minute (ASR-22).
- **Uploads wait with the draft.** An image or attachment added, replaced or removed during a hold is held in the database beside the draft's text, covered by the same point-in-time recovery, and written to the repository in the commit that finishes the session.
- **There is no Save.** *Finish editing* opens the send-for-review screen (DL-0222). It presents the holder's changes (*my edits*), the part operations and the change summary, which starts from a mechanical draft naming the sections touched (DL-0261) and stays in the language its writer left it in, the fixed lines the platform itself writes translated when drawn (DL-0501); the companion analyses join it in release 0.2. The editor continues editing, discards the draft after confirming, or commits — *send for review* for a holder of *edit* alone (DL-0054), *create version N.M-X* or *accept as N.M* for a holder of *accept*. A session that changed only attachments or appendix order ends the same ways; discarding it leaves every file as it was, a deletion included (DL-0180).
- **From release 0.2, the analyses are written into the same commit** as the content, in `analysis/` (DL-0055); release 0.1 writes none (DL-0261). This is why the commit identifier is never needed: the analysis is part of the tree rather than a pointer at it, both halves are known before the commit is made, and the reasoning travels into any clone or export.
- **Analysis files have fixed names and are overwritten on every commit** (DL-0067). Nothing is lost — the analysis as of any version is `git show {commit}:analysis/{name}`. Accumulating timestamped files would duplicate what history already gives.
- **Only the editor-facing artefact goes into the tree.** The reviewer-eyes-only analysis (DL-0007) must never be committed into the document folder, because anyone with read access to the document would read it. It lives outside the tree, reachable only through the access table. Committing it would breach ASR-03 by a storage decision rather than a delivery one.
- History is **linear and append-only** (ADR-0003, ASR-02). No branches, no merges, no rewriting. An unwanted change is undone by reverting it into the reviewer's draft — one version, or one author's versions since the last acceptance — computed by walking the run forward from the last acceptance, moves followed by the platform's rule (ADR-0011, DL-0425); lines a later version changed are left for the reviewer to edit by hand, and the draft is committed as the reviewer's version (ADR-0015); see § History, comparison and undo.
- **`refs/proposals/{id}/head` is no longer needed** — nothing is squashed, so nothing needs retaining. ADR-0002's retention consequence lapses.
- **Acceptance** is a commit to the document's passport carrying the reviewer's decision, so approval history lives in the repository and travels with the document (DL-0041). **A reviewer's corrections are versions of the run**, never part of the acceptance commit: an editing session finished by *accept as* or *create version* (DL-0222), or an undo applied to the reviewer's draft (ADR-0015). A version committed by a holder of *accept* is marked so at commit (ADR-0014). An acceptance or a version stopped after its commit and before its rows is settled — its rows derived, an acceptance's from its passport section, its notices computed — by the next writer under the lock before its own commit, and by the reconciler, so a number is never given twice and nothing is written over a commit the rows do not know (DL-0111).
- **Returning a run** is a passport commit of its own kind (DL-0114): the reviewer, the reason — one line of at most 500 characters (DL-0378) — and the last version of the run it returns, then its `RETURN` row and the run's authors notified, the reason in the application alone (DL-0369). It is refused while the document is reserved, with nothing to return, by a non-reviewer, after the run grew since the confirmation, and over a run already returned with nothing sent since. A return stopped after its commit is derived by the next writer and by the reconciler, from its section, as an acceptance is; the reconciler also checks every `RETURN` row against its section. The run stays pending: the document reads *returned* until a version is sent after it, an acceptance ends it, and *In review* leaves it out meanwhile (DL-0420).
- **Version numbers are derived** (DL-0183): an acceptance is `N.M` — N canonical editions before it, M acceptances since the last — and making a document canonical gives its latest accepted version `N+1.0`. The passport records them, so no user ever needs a commit hash. Pending work is shown as the later of the latest edition's and the latest accepted number, plus the content versions since it — `edit` and `reviewer_edit`, never a passport commit — `1.3-2`, and `2.0-1` for the first after edition `2.0` (DL-0267). Before the first acceptance the base is `0.0` — the document's first version, the text as created, which reads `0.0` wherever a version is named — so the first content version reads `0.0-1` (DL-0272, DL-0358).
- **Copying a document creates a new one** (ADR-0007): its first commit, of kind `created` (DL-0268), holds the chosen version's text — canonical, accepted or pending — with the chosen appendices, the images their texts reference and the declarations they mark, no attachments and no history. It is author-only until groups are linked, and records its source. The source version is read once under its writer lock and matched against the number the dialog showed, a moved one refused; the source is written to the audit trail before the repository exists, so a copy that stops is recognised: the reconciler reports it `copy_stopped` and never finishes it from the template, and the operator removes it with `remove_stopped_copy` (DL-0455, DL-0451).
- **A freeze locks the document, not a version** (DL-0189). A document is frozen only when nobody holds it; while frozen, only holders of *accept* may take the hold (ADR-0016); their commits and acceptances continue the numbering. **Make canonical needs no freeze** (DL-0515): whoever may make the document canonical makes its latest accepted version the next edition, frozen or not, while nobody holds the document (DL-0419) and no content version since that acceptance is unaccepted (DL-0267), the distinct-approver check standing where the organisation has it on (DL-0115). It **writes a passport commit** — the approver, the edition number and the accepted version it approves — **and tags it** as the next edition, ending the freeze where one is open (DL-0260); an approval with no freeze open records a freeze begun and ended at the approval, written with it, so every edition keeps the freeze it ended and History draws none for it (DL-0515); *unfreeze* ends a freeze without one. An approval stopped after its commit is finished — tag, rows, the freeze's end — by the next writer under the lock and by the reconciler, from its passport section, as an acceptance is. **Which version a person reads** is one function of their rights (DL-0209): the latest content version for *view pending*, the latest accepted for *view accepted*, the latest edition for *view canonical*, before whose first edition the document does not exist for that reader; the page, the list's *Canonical* and *Latest* columns and the attachment route all read it.
- **Acceptance is document-level** (DL-0090): one reviewer accepts the whole run since the last accepted version. No per-file ledger, no partially-approved state, no section owners (DL-0091).
- **Holds** are exclusive per document and taken by *Edit* on the document page, which opens the editor (ADR-0006, DL-0319, DL-0518). **The quiet hold:** a hold not reserved and idle for the tenant's period — 30 minutes by default — is prompted: the heartbeat answers that it is idle and an open editor asks whether the holder is still working — a tab with no editor open is told by the notification alone — and a worker task, every minute, notifies the holder once per idle spell. Ten minutes later, still idle, the task releases it for inactivity (DL-0377). The prompt is derived from the hold's last activity, never stored; answering it restarts the clock only while it is asked. A tenant or platform administrator can force release an ordinary hold, and blocking the holder releases it (DL-0256). **The released draft is kept when it has edits** — a hold with none keeps nothing, its draft deleted as the hold ends (DL-0514) — for its holder, who is offered it back before any new hold: if nobody has committed since, the take-back moves the draft to the new hold; otherwise it opens read-only as changes against the current text or another version the holder's rights reach — the pending run, the latest accepted version, the latest edition, and what a history right adds (DL-0417) — and may be discarded (DL-0318, DL-0379, DL-0381). The head decides: a new version, an acceptance or a return since the draft began rules out the take-back. **A release that keeps a draft first completes a finish that stopped after its commit** — the record settled, the hold released `finished`, the reviewers told — and nothing is kept (DL-0414). A holder's *discard my edits* deletes the draft and its files under the document's locks, and is refused while an editor is open.
- **A reserved hold** carries `reserved_at` and is skipped by the inactivity release (ADR-0009); nothing else about the hold changes. As for any hold, freezing, group-link changes and editing by anyone else are refused; while it is set, acceptance and return by anyone else are refused too, and the holder's own *accept as N.M* ends it. Starting, cancelling and ending it are audit events. An administrator ending it — on a page naming the reservation, so a newer one is never ended by a stale page (DL-0415) — records a reason, an audit event and a notification; the reason is read in the application and never travels by email (DL-0369). *Accept as N.M* runs the commit and the acceptance under the one single-writer lock, so no other ref update falls between them.

### History, comparison and undo

- **One reader of the past** (ADR-0007, DL-0209, DL-0286). What a person may open of a document's history is computed once per request: a viewing right reaches the current version of each stance it includes — the latest edition, the latest accepted version, every version of the run — and a history right widens it within those stances, never past them: *view previous canonical versions* adds every edition, *view all history* every content version up to the latest the reader's ladder reaches. Every page that opens a past version, the export at a version, the compare page, the kept draft's chooser and a notification's link read it, and a number it does not reach answers as a missing one; a forbidden number costs exactly what a missing one does (ADR-0008).
- **Numbers resolve both ways.** A version's number is derived from git and the passport: a content version shows the highest stance it reached — the edition's number, else the acceptance's, else its pending number — and every number it ever carried names it, so `0.0-3` and the `0.1` that accepted it open one version. A passport commit shows the number its section names; a return, the number its version carried when it was returned.
- **History**, an icon in the document page's heading (DL-0518), lists the versions newest first, with the freezes and unfreezes between them, the line where accepted text ends drawn to a reader of accepted text; its breadth is the history rights' and *accept*'s (DL-0251).
- **Compare** renders the newer of two versions with its changes against the older, whichever order asked — or, with `with`, the second of two documents against the first, in the reader's order, each version through its own document's ceiling and each document's attachments listed apart (DL-0452); attachments are listed as added, changed — file, title or file name — removed or unchanged; appendices are compared in pairs the reader picks, one of each version or of each document, on a page of the same shape (DL-0187, DL-0208); on every comparison of two versions, *‹* and *›* — *previous* and *next* — step out of it: for X against Y, *‹* opens the version before X against X and *›* opens Y against the version after Y, a version the reader may not see skipped (DL-0209), each disabled when no such version exists; a comparison of two documents has neither (DL-0508).
- **Undo** (ADR-0015, DL-0243, DL-0425). The reversal reads the repository once for `document.md` and once for each appendix the run touched — the file at the last acceptance, or the empty file for an appendix the run added, and the run's `-U0` log of it — and walks the run forward with the correction notice's walk, carrying each line's writer and following moves by the platform's rule, so a third rule never exists. Every line an undone version added or removed is *clean* — reverted — or *built on*, when a version not undone changed it: left as it stands and listed for the reviewer's hand — its wording before, what the undone versions wrote there, and what stands now — except a line a later version deleted outright, or rewrote and a later one deleted (DL-0422). The body of `document.md` and each appendix's text are reversed, an appendix's listed places carrying its title; a title or part operation of an undone version — an appendix it created or deleted among them — is listed, to be reverted with the parts' own controls (DL-0447). The reversal is merged into the reviewer's draft line by line, three ways from the text the draft was last derived from, so a second undo never types a line twice and a line the draft already changed is listed, never overwritten. The listed places are kept beside the text in the draft's record, never in it (DL-0380). The reviewer's hold is opened only in the transaction that writes, so a refused undo leaves nobody holding the document; the record is settled under the writer lock before that transaction, as every writer settles it. An editor open on the draft is told it is stale at its next capture and keeps its text. While the undo waits in the draft, *Accept the run* is refused, naming whose draft holds it, and the run is accepted through that draft's *Accept as* (DL-0427). Over a two-hundred-version history the walk takes a tenth of a second (V-14, DL-0135), and the walk of a body and five appendices half a second (V-17).

## The pending view

A plain read, not a computation over branches: the content versions since the last accepted revision, in order, attributed — the run's lines by a blame of the head bounded by the accepted version, the accepted text's from its kept rows. **The document's review state** is a function of the acceptances, the repository and the linked groups' rights and the returns — never a stored column beside `DOCUMENT.state`'s lifecycle; a document whose linked groups hold no *accept* has no reviewer whatever else is true, and the tags that speak of pending work reach only holders of *view pending*. **Changes are shown word by word inside the rendered text** (DL-0170): the line diff finds the changed sentences, and only those are compared word by word; a change to formatting alone carries its own marker. Added, replaced and removed images and attachments are listed with their titles, each version viewable or downloadable. *My edits* — a switch inside the editor (DL-0518) — uses the same presentation against the current text, and so does a comparison of two different documents, each at a version the reader may read (DL-0187). Sentence-per-line keeps attribution exact, so *Show edit authors* (DL-0040, DL-0489, DL-0504) resolves to a sentence rather than a paragraph, and a per-author revert is exact.

**The run is read on the review page** (DL-0518, DL-0509), which a holder of *accept* opens from the latest version on the document page's path while a run is pending: the run's text with its change authors; in the right panel, the run's versions with their summaries, authors and dates, with *undo this edit* and *undo all of this author's edits*; the run's part operations and *revert*; *accept* and *return*; and the freeze toggle. A reader of pending work without *accept* reads the run on the same page, which the path's arc from the latest accepted version to the latest opens: the run's text with its change authors, a changed image before and after side by side and the run's part operations, read-only — the review page without its acts (DL-0522).

## Presence

Derived, never declared (DL-0036). That a document is held is shown to everyone who may read it, in the list and on the document; who holds it, for every hold, ordinary or reserved, to holders of *edit* or *accept* on it and to administrators — *редагує {name}* under the latest version, and as the reason beside a disabled *Edit* (DL-0516); everyone else sees the fact alone. Content stays invisible until the version is committed.

## Rejection records

Rationale and rejected alternatives: [`ADR-0001`](adr/ADR-0001-reviewer-corrects-and-accepts.md).

Generated, not authored (ADR-0014). **At acceptance**, for every version of the accepted run committed by a holder of *accept* — a correction, an undo, a session finished by *accept as* — the platform diffs that version against its parent; each change of the pending run it replaced or reversed — a line written, a line removed and now restored, an appendix or attachment operation reverted — becomes an entry holding **references, never text** (DL-0113): the changing version and its author, the change's author and the version that made it, and the file with the line range in the author's version and in the accepted version, or the part for a file operation. **An author receives one notice per acceptance**, listing every entry for their lines. The acceptor's own versions in the run count as a reviewer's, whatever their stored kind. A line the move rule recognises as moved (ADR-0011) is neither replaced nor removed. Nobody is notified about their own lines. Other versions committed by editors without *accept*, a document's `created` commit (DL-0268), and lines already in the accepted text, generate nothing. Both wordings are rendered from git when the notice is opened, under the reader's **current** rights — so a revoked right or an archived document withdraws the text, which a stored copy would not.

**No notification carries document text**, in the application or by email. Email carries the event and a link. The editor may escalate a record into the Statement of Disagreements; editor and reviewer may settle an entry by agreement with exactly one wording surviving, and on deadlock the decider rules, and only the decider can (DL-0026).

## Comments

Threads anchored to a passage or to an edit, nested, closable, permanently recorded. Nothing is written into the document text: commenting must not require the right to edit, so no marker can be placed in the source to hold an anchor, and comment traffic would pollute the sense-versus-style classifier.

The thread store is in Django, with anchors modelled on the W3C Web Annotation Data Model — a quoted-text selector plus a position selector — resolved against the sentence-per-line source (DL-0027). When the anchored sentence later changes, the thread is flagged as attached to a superseded sentence and shown with both wordings rather than silently re-anchored. A snapshot exports into the document folder whenever an edition is frozen.

## Heuristics, actions and prompt composition

Three levels (DL-0049, refining DL-0031):

| Entity | Contents | Composed into |
|---|---|---|
| **heuristic** | one focused piece of prompt text | actions and side-document types |
| **companion action** | a set of heuristics | a user-facing analysis, run against one version |
| **side-document type** | a set of heuristics | a generated view, recompiled on every commit |

The **platform administrator** creates and edits all three. The **tenant administrator** sees titles and descriptions of actions and side-document types and attaches them to documents, and cannot see heuristics at all. The **editor** calls actions and reads views, and sees neither heuristics nor the sets. The taxonomy in [`review-findings.md`](review-findings.md) is the specification the catalogue's prompt text is written against; the text itself is source (§ Prompts are source).

**Run provenance is recorded** — every agent run stores the exact heuristic set and the version of each heuristic's text it used, and every finding carries the heuristic that produced it. A finding that shaped an approval has to remain explainable months later, which requires knowing the heuristic text as it was, not as it now is.

Inside the platform, prompt text is reachable only by the platform administrator: reading and configuring heuristics is that role's privilege, and a tenant administrator or a user has no need for it. The same text is source in this repository (§ Prompts are source), which is where it is reviewed and versioned.

## Prompts are source

**Heuristic prompt text is source code, and `prompts/` in this repository is canonical while the product is being built.** One directory per heuristic at the repository root, plain Markdown loaded by path — never packaged as module data, so it can be read and edited by someone who does not write Python. Its eval cases live beside it in `evals/` ([`evaluation-strategy.md`](evaluation-strategy.md)). A prompt enters `prompts/` when it has cases to be measured against.

- **A seed command derives the database copy.** The heuristic rows the platform administrator sees are loaded from `prompts/` — idempotent, re-runnable, each row recording the source version it came from. That source version is the *heuristic version* run provenance records, and the one a review scope's heuristic set version is built from.
- **An in-place edit is a divergence, not a new source of truth.** The platform administrator may edit a row as a hotfix. The seed command reports every row that differs from its source, and the edit is folded back into `prompts/` or overwritten — it is never left as the only copy.
- **Selection is data.** Which actions and side-document types a tenant enables, and on which documents, is ordinary configuration and lives only in the database.
- **When the platform's own versioning is mature, the canonical copy may move into it.** The repository then keeps a **published export of each released heuristic set**, generated at release by the same command. Without it the prompt work becomes invisible outside the running system — no diff, no review, no citable history.

## Agent scopes and finding lifecycle

The companion is **edit-scoped**; the reviewer agent reports both introduced and pre-existing findings, in separated groups (DL-0032).

The mechanism is a **standing findings set** per document, computed against the accepted state and refreshed when that state changes. A run's findings are computed against its latest version and diffed against the standing set, classifying each finding as **introduced**, **pre-existing**, **resolved** or **aggravated**. The standing set is computed once per accepted state and shared across every unaccepted run, so the cost does not scale with the number of open runs, and it doubles as the known-open-findings list on a canonical document.

## The reviewer agent

Runs when a document is **sent for review** (DL-0054) — never on a draft before it is sent — as a sandboxed container job with read access to the document repository and the confidential guidance document, and write access only to its own two output artefacts.

It produces two artefacts from **two runs with different inputs** (DL-0095, refining DL-0007):

1. A **reviewer-eyes-only analysis** — a run that reads the guidance, free to cite it.
2. An **editor-facing analysis** — a run whose context **never contains the guidance at all**.

Only the second is publishable, and only when a human reviewer releases it. Two runs rather than two outputs of one run is the whole control: with the confidential material absent from the context that writes the publishable artefact, a prompt failure, a model error or an instruction injected into the document cannot carry it across (`threat-model.md` T-01, T-02).

## Findings and their audience

The agent tags each finding with the material it was derived from. The platform applies DL-0021: a finding reaches a recipient if and only if it is derivable from material that recipient may already read. Audience is computed **per recipient**, not per finding — a finding drawing on a neighbouring document is ordinary for a reviewer who may read both and confidential for an editor who may read only one. An untagged finding is treated as reviewer-only. The decision is the platform's, never the prompt's.

## The companion agent

Runs against the editor's session with its own interface. Sees the working document and the canonical documents its editor may read. Never sees the confidential guidance document. Also generates the length-limited change description the editor may accept or edit (DL-0039, DL-0261).

## Export

Markdown, PDF and DOCX, all from one parse (ADR-0013). The Markdown export is the text as the source view shows it, its headings numbered (DL-0363); a text holding images is one zip, the `.md` file beside an `images` folder. PDF and DOCX embed the images, a JPEG standing as its orientation tag says, and a marked export shows a changed image before and after, the before side read at the baseline (DL-0472, DL-11-003). **A mention is plain text in PDF and DOCX** for every requester, and the stored span in Markdown (DL-0438). PDF is weasyprint over the HTML the server's parser renders, with the organisation's stylesheet, fetch failures fatal and the fetcher limited to repository files. DOCX is Pandoc over that same HTML, the platform's classes mapped to named Word styles whose look a reference document derived from the stylesheet provides (DL-0465). The validator gates every export; a renderer's warning is never a pass. All three are in stage 1 — Markdown made the Word path cheap (DL-0046).

**The stylesheets a PDF is rendered with, in order** (DL-0464, DL-0477): the platform's default, the page furniture, the organisation's stylesheet as written — after the furniture, so its page size and margins win within the checker's bounds — and the platform's guard last. **The Word file's reference document is derived, never uploaded** (DL-0465): a fixed mapping from selectors and properties to Word's named styles — headings, body text, quotations, callouts, the marked roles, actions and terms, clause numbers, the title page's details — sets each derived property into Pandoc's own reference document, and the page's size and margins into its section; it is remembered per stylesheet, and what cannot map is listed on the styles page, by line. A picture turned or in a table cell is fitted to the derived page's text width.

**The styles page tries a stylesheet before it is applied** (DL-0466): *Export a sample PDF* or *Word file* renders a built-in invented text in the requester's interface language (DL-0498) — every construct the whitelist allows, a title page of invented facts in the organisation's layout, an attachment list — through the export's own composition, with the text in the box. One sample is queued or running per organisation; the row is written and audited before it is queued, failed when the queue refuses it or it has waited half an hour unheld, and its file is swept with the exports after a day.

**Export is a page of the document's own**, opened by the Export icon in the document page's heading; its heading names the version it will export, following the view chosen (DL-0518, DL-0519). An export is composed there from three choices (DL-0172, DL-0193):

- **What** — checkboxes, all checked by default: the document; its appendices, embedded in the document or as separate files; its attachments, as stored. A part the document does not have is not offered.
- **Format** — one of DOCX, PDF, Markdown.
- **View** — the canonical version; the *accepted* version; *pending edits*, marked against the last approved text; *my edits*, marked against the current text, or unmarked — each as the reader's rights allow (DL-0209). Change marks appear in DOCX and PDF only.

More than one file is always delivered as a zip. A single attachment is downloaded from the document page; there is no single-item export. Every attachment put in a zip is checked against its listed hash, as its download is, and a mismatch fails the export. An embedded appendix follows the body, before the attachment list, rendered alone — its numbers from 1, its title never printed (DL-0165) — and starts a page of its own in PDF; a separate one is a file of its own in the zip, named by its number and title.

**An export asked from a version's historical page** exports that version alone, its view by the stance the version reached, marked by that stance's chain as the export page marks it — an edition against the previous edition, accepted text against the edition before it, pending work against the acceptance or edition it counts from — where the reader's ceiling reaches the baseline, and with the page's default (DL-0426). The file carries the number the version's page shows. Its job records that it was asked at a version and, when it runs, re-checks the reader's ceiling — for the version and its baseline — rather than the view's rights: a version reached through a history right exports to the end, and a right lost after asking fails the job (DL-0423).

**An exported file is named `<title>_—_<version>_—_<stance>.<ext>`** (DL-0275) — the title as typed, the version number and the stance, every space an underscore, every character a filesystem refuses a hyphen, and control characters, direction marks and line separators dropped; a zip takes the same name. A **marked** export adds a suffix naming the marks after the stance — `<stance>-<marks>.<ext>` — so a marked and a clean export of one version never share a name. **Every word of the export's own is in the document's language** (DL-0502): the stance and the suffix in the name, the fixed words inside a zip — the document, each appendix, each attachment — and the words of the title page and the attachment list, with the glossary's terms, whoever asked for it and whatever the installation's language; a word the catalogue does not hold in that language falls back to English.

The platform generates two parts no one authors: the **title page**, when the document has one, and the **attachment list** — title, file name and SHA-256 hash, on a page of its own in DOCX and PDF and as a final `#` section in Markdown. Attachment contents are never embedded in a text export.

**The frontmatter is never exported**, in any format: it is the platform's record of the document's parts and settings, not text anyone wrote for a reader (DL-0181).

**DOCX and PDF carry page furniture** (DL-0182, DL-0362): the page number in the footer, and no header. The title, the version and the stance the export shows — canonical version, accepted edits, pending edits or my edits — stand in the file's name, and on the title page where the document has one; a *pending edits* or *my edits* export names the last accepted number plus the content versions since it (DL-0267): `1.3-2`.

## Analysis scope, storage and cost

The same edit yields different findings for different readers: an editor who can see one document, a finance director who can also see a neighbouring one, a chief executive who can also see the confidential guidance. Three rules keep that from multiplying into chaos.

**A review runs under the reviewer's own access** (DL-0077), over a **scope the reviewer selects** — access is not relevance. Findings are tagged with the sources they were derived from and filtered per recipient (DL-0021); the editor-facing artefact comes from a run that never held the confidential material at all (DL-0095), so the control is both the filter and the absence.

**Storage follows provenance, not the user (DL-0069).** A finding derived from the document alone — class P1 — is committed into that document's `analysis/`. Anything derived from other documents or from the guidance lives outside the tree; committing it into a document folder would hand it to everyone who can read that document.

**Keyed by review scope, not by user** (DL-0078). A scope is the ordered set of documents a reviewer put in scope, their content states, and the heuristic set version. Two reviewers with the same scope share one result; different scopes lose nothing. This answers "is it document analysis or user analysis": it is corpus analysis keyed to a scope, anchored to the document whose commit triggered it.

## Types, folders and links

- **Document types** are a table in each tenant's schema, maintained by its tenant administrator and seeded with one type, *document*; assigned per document, used as list filters (DL-0057, DL-0063, DL-0235). A label is unique in any case; a type no document carries may be deleted, the seeded one only renamed or retired; a retired type stays on its documents and is never offered; the last type not retired is neither retired nor deleted (DL-10-001, DL-10-002). A document's type changes on its *Info* page, an icon in the document page's heading (DL-0518).
- **Folders** are metadata with unlimited nesting; storage stays flat (ASR-15). A person sees only folders holding, at any depth, a document they may read; administrators see all (DL-0206). The tenant administrator creates, renames and deletes an empty folder and moves documents; a name is unique among its siblings in any case, and the root is the tenant's (DL-0453). The corpus's acts lock in one order — a folder, then documents, then a type — so none waits on another in a circle.
- **Search** reads titles — a document's, and an appendix's at a version its reader could read — never text: its candidates are chosen from the database alone, the same rows whatever the words, then each is confirmed against the version its reader reads (DL-0197, DL-10-003); the type filter opens search for one type across every folder (DL-0236, DL-10-004).
- **Archiving** sets the state, releases an open hold, a draft with edits kept (DL-0514), and tells its holder, and leaves the links as they stand (DL-0084, DL-0449, DL-0456, DL-0471); an archived document is reached by administrators alone, read only (DL-0450).
- **Outline** — every document renders a navigation outline of its sections and subsections.
- **Links** resolve per reader: a mention — `[words]{.document #12}`, another document named by its number (DL-0436) — becomes a link only if that reader may read the target while it is active, and renders as its words alone otherwise, an archived target and a number that names none included (ASR-16, DL-0084); a mention of the document itself is its words alone for every reader (DL-11-012). The generated **see also** applies the same filter, listing an unreachable target by the mention's words (DL-0437). The filter runs at render time against the access table, never at authoring time.

## Generated views and document ADRs

No human editor (DL-0044, ASR-09), and their author is shown as the **system** (DL-0448). **The role directory and see also are derived at render** from the version shown — no store, no agent: each role the document declares or marks, with every heading and clause marking it, and each mentioned document once (DL-0073, DL-0437). From stage 2 the agent writes the others. Of those, **mandatory** views recompile on every commit; **voluntary** views are generated on request and may seed an authored document, which is then a copy under human authorship rather than an edited view (DL-0063). Stage 2's mandatory set: the control directory, and the standing contradictions, ambiguities and blind-spot lists; each carries its own history, and the role directory stays derived at render. For a holder of the guidance grant, each list also carries an addendum computed against the confidential requirements and visible only to them.

Document ADRs (DL-0045) are generated when a person changes the document's logic rather than its wording: one record per decision, however many passages it rewrites, pre-authored by the agent and editable by the person.

## Agent invocation rules

- **No free-form channel.** A user calls a predefined action; nobody composes a prompt (ASR-11).
- **Actions may run at any time**, including mid-edit, and the editor picks which ones.
- **Results are keyed to a hash of the document tree**, not to a commit (DL-0056, ASR-12). One model call per action per content state; a repeat returns the stored result. A commit is one content state among others, which is why the send screen shows work already done.
- The reviewer agent runs on the commit that *send for review* produces, and reads the analyses committed alongside it.
- Each run mounts read-only exactly the repositories in its review scope. The editor-facing run's scope excludes the guidance, so DL-0095's containment is a mount table rather than a property of prompt assembly.

## Notifications

An in-application notifications section, email for the same events, and document-list state as the standing picture of what is waiting (DL-0070). A tenant may send from its own address, or from the platform's by default; every sending password is encrypted at rest under a key from the environment, decrypted only in the worker when sending, and write-only in the interface. *Send a test email* sends from the configured address to itself and reports each step (DL-0202). **Every email goes through an outbox** written before the first attempt: three attempts five minutes apart, then *failed* with an in-application notice to administrators; the outbox is the log of every notification email sent (DL-0203); a test email goes to the server directly, its latest steps alone kept on the sender row (DL-0392). Links in an email are built from the tenant's default host, or the platform's (ADR-0008). **An email is written in its recipient's interface language**, fixed when it is queued; an invitation's always in the installation's default, since an administrator reads the outbox and an invitation in another language would tell them the address already has an account with that preference (ASR-17, DL-0501). Notifications are shown in two tabs, *Document* and *Administrative* (DL-0204). A correction notice is one notification per author per acceptance, however many of their lines changed (ADR-0014). **No notification carries document text** (DL-0113, DL-0205): an email may carry the document's number and title, versions, people, the event and the state, and a link — never any text of the document or its appendices, and never the change summary.

**As built.** One writer, `notifications.services.notify`, records an organisation's notifications in its schema; `notify_platform` records a platform administrator's in the shared schema's `PlatformNotification` — a backup condition, a failed email — since a platform administrator may belong to no organisation (DL-0382). Nobody is told of their own act. A notification's row carries ids and numbers only (DL-0370); its text is composed when it is shown or emailed. **The queue rule:** each notification queues one email in the same transaction, in the current schema's outbox, from that schema's sender or else the platform's; with neither, none (DL-0367). Three exceptions: a failed email is told in the application only; the group entries an invitation writes carry no email, the invitation's own being the one its person receives (DL-0399); and no email is queued about a document its person cannot open (DL-0386). An invitation and a reset queue their own email, not a notification's, and the outbox row records its kind: a reset's row — in the organisation's outbox when it was asked for on that organisation's domain (DL-0383) — is listed to a platform administrator alone, and its failure is told to the platform alone (DL-0410). **The task:** `mail.send_outbox` runs every minute, claims each due row with a lock that skips rows another run holds, and sends it in a transaction of its own — the shared schema first, then each organisation the background work visits; a failure in one schema or with one email stops no other. A run claims no row after 45 seconds, and the scheduler drops a run it could not start within 50, so runs never pile up behind a slow server. Before sending, the recipient's right to the document is read again: an email about one they can no longer open fails with no notice (DL-0387). A refusal is recorded as a reason code with the server's answer, never an exception's text, and tried again five minutes later until the third, which fails the row and tells the organisation's administrators and the platform's — a reset's, the platform's alone, its notice naming the organisation whose outbox holds the row. An email links to the notification it carries, which marks it read and leads where the entry leads (DL-0394). With no sending address left, an email waits, its attempts untouched, until one is set (DL-0395). The platform's mail pages read and write the shared mail rows through the schema context manager inside their requests, as the queue reads the platform's sender (DL-0367, DL-0393). **The keys:** sending passwords are encrypted with Fernet under `MAIL_PASSWORD_KEY`, read when used, never at start (DL-0384); `MAIL_PASSWORD_KEY_PREVIOUS` still decrypts during a rotation, and `rotate_mail_key` re-encrypts every stored password under the current key. Without a readable key, or with a key that does not open the stored password, an email of a sender that signs in waits, its attempts untouched, under a reason of its own, logged once (DL-0389). A sender that signs in nowhere stores no password, and the rotation passes it over. A stored password is kept only while the server it was entered for — host, port, connection and user name — is unchanged (DL-0390); a sign-in over an unencrypted connection is allowed only to the same machine (DL-0388). *Send a test email* runs in the worker, one at a time (DL-0392), and reports *connected*, *signed in* and *sent* apart.

**The menu's two views.** *In review* lists the documents the person may accept whose list tags read *awaiting review* — and *returned*, once returns exist — frozen ones included (DL-0351); *Being edited* those they may edit whose text lies beyond the latest edition. Every page's menu asks only whether each view holds anything, and stops at the first document that does; a view's own page answers for its link (DL-0197).
